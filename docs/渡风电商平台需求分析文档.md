# 1. 引言

## 1.1 编写目的

本文档旨在明确渡风电商平台的系统边界、业务目标、功能需求与非功能需求，作为后续**系统设计、开发、测试、验收及运维**的基线依据。目标读者包括：

- 产品经理：明确需求范围与优先级
- 架构师 / 后端开发：指导后端服务划分与接口设计
- 前端开发：明确页面与交互需求
- 测试人员：编写测试用例与验收标准
- 项目经理：预估工作量与排期
- 运维 / 安全人员：明确部署与安全要求

## 1.2 项目背景

随着互联网消费习惯的成熟与移动端渗透率提升，企业需要一套自营可控的电商平台，以支撑品牌商品的在线销售、订单履约、售后与营销运营。渡风电商平台定位为**B2C 自营 + 商家入驻**的综合性电商系统，面向消费者提供一站式购物体验，同时为运营团队与入驻商家提供管理能力。

当前市场对系统的**稳定性、响应速度、数据安全、可扩展性**提出较高要求。因此，项目采用前后端分离架构：后端基于 **Spring Boot** 构建模块化单体应用，前端基于 **Vue 3** 构建响应式单页应用（SPA），并结合主流开源组件快速落地、按需演进。

# 2. 项目概述

## 2.1 产品定位

渡风电商平台是一个面向消费者、入驻商家与平台运营人员的**多角色电商系统**，核心目标是：

- 提供流畅、安全的在线购物全流程
- 支持商家入驻与商品自营双模式运营
- 提供订单、库存、营销、售后等电商核心能力
- 提供数据看板与经营分析，支撑精细化运营
- 采用模块化、可扩展的技术架构，支持后续向微服务演进

## 2.2 项目目标

| 目标 | 描述 | 衡量指标 |
| --- | --- | --- |
| 业务目标 | 上线后支持商品上架、下单、支付、履约闭环 | 核心交易链路可用率 ≥ 99.9% |
| 用户目标 | 消费者可便捷浏览、搜索、购买、售后 | 核心页面加载时间 ≤ 2s |
| 商家目标 | 商家可自主装修店铺、管理商品与订单 | 商家日常操作可自助完成 |
| 平台目标 | 运营可配置类目、营销、内容与权限 | 配置操作在线化、可审计 |
| 技术目标 | 前后端分离、接口规范、易于扩展 | 接口统一规范、分层清晰 |

## 2.3 目标用户与角色

系统包含三个使用端，对应五类核心角色：

| 使用端 | 角色 | 说明 |
| --- | --- | --- |
| 前台（消费者端） | 游客 | 未登录用户，可浏览、搜索，部分操作受限 |
| 前台（消费者端） | 注册用户 | 可下单、支付、评价、售后、使用优惠券 |
| 商家端 | 商家管理员 | 管理店铺、商品、库存、订单、营销、售后 |
| 平台端 | 平台运营 | 管理类目、营销、内容、商家/商品审核 |
| 平台端 | 平台管理员 | 系统配置、权限管理、数据看板、日志审计 |

## 2.4 运行环境

### 2.4.1 客户端

- 浏览器：Chrome / Edge / Firefox 最近两个大版本
- 终端：桌面端为主，兼容移动端（响应式）
- 分辨率：≥ 1280×720 桌面；移动端 ≥ 375px 宽度

### 2.4.2 服务端

- JDK 17 及以上
- Spring Boot 3.x
- MySQL 8.0（主库）
- Redis 7.x（缓存 / 会话 / 分布式锁）
- RabbitMQ / RocketMQ（异步消息，可选演进）
- Nginx（反向代理与静态资源）

### 2.4.3 前端

- Vue 3（Composition API）
- Vite 构建
- Pinia 状态管理
- Vue Router 4
- Element Plus / 自定义 UI 组件
- Axios 请求封装

## 2.5 技术架构

系统采用**前后端分离的三层架构**，后端基于 Spring Boot 采用模块化单体（Modular Monolith）设计，前期以单体快速交付，后期可按领域拆分为微服务：

```text
┌──────────────────────────────────────────────┐
│                 客户端 / 浏览器               │
│   Vue 3 SPA（前台 / 商家端 / 平台端）        │
└───────────────────┬──────────────────────────┘
                    │ HTTPS / RESTful API
┌───────────────────▼──────────────────────────┐
│               网关层（可选 / Nginx）          │
└───────────────────┬──────────────────────────┘
┌───────────────────▼──────────────────────────┐
│             应用层（Spring Boot）             │
│  Controller → Service → Mapper/Repository     │
│  认证鉴权 · 参数校验 · 统一异常 · 幂等控制    │
└───────┬──────────────────────┬───────────────┘
        │                      │
   ┌────▼─────┐           ┌────▼─────┐
   │  MySQL   │           │  Redis   │
   │ 主数据    │           │ 缓存/锁  │
   └──────────┘           └──────────┘
```

## 2.6 设计约束与假设

- 服务端与客户端严格分离，数据库不得直接暴露给前端。
- 所有接口遵循 RESTful 规范，统一返回结构。
- 认证采用 JWT + Redis 会话黑名单机制。
- 前期采用模块化单体，不强制拆分微服务，但模块边界需清晰。
- 假设网络环境稳定，数据库与缓存服务可用；假设运营人员具备基本电商操作常识。
- 假设商品数量、订单量在初期符合中小规模电商水平，具备横向扩容空间。

# 3. 总体需求描述

## 3.1 需求范围

本项目覆盖电商核心交易链路与配套管理能力，具体范围如下：

- **范围包含**：用户体系、商品、类目、购物车、订单、支付、促销/优惠、库存、售后、评价、商家管理、平台管理、数据看板、消息通知。
- **范围不包含（本期）**：跨境贸易、多物流渠道深度对接、直播/短视频带货、供应链 ERP 系统、财务总账系统。

## 3.2 系统功能架构

系统按 **前台（消费者） / 商家端 / 平台管理端** 三大子系统划分，功能模块如下：

| 子系统 | 模块 |
| --- | --- |
| 前台消费者端 | 首页、商品检索、商品详情、购物车、结算下单、支付、订单中心、售后、评价、收藏、优惠券、个人中心、消息中心 |
| 商家端 | 店铺管理、商品管理、库存管理、订单管理、售后管理、营销管理、经营数据 |
| 平台管理端 | 用户管理、商家管理、商品审核、类目管理、品牌管理、订单监管、营销管理、内容管理（公告/轮播）、权限管理、系统配置、数据看板、日志审计 |

## 3.3 角色与权限矩阵

| 功能模块 | 游客 | 注册用户 | 商家管理员 | 平台运营 | 平台管理员 |

| 购物车 | ❌ | ✅ | ✅ | ✅ | ✅ |

# 6. 业务流程

## 6.1 注册登录流程

1. 用户输入手机号/邮箱与验证码进行注册校验。
2. 系统校验唯一性，成功后创建账户并锁定当前会话。
3. 用户可选择绑定登录方式（密码/验证码/第三方）。
4. 登录鉴权成功后签发 JWT 并写入 Redis 会话。
5. 退出登录时清除会话并加入黑名单。

## 6.2 商品购买流程

```text
浏览/搜索商品 → 查看详情 → 选择SKU → 加入购物车/立即购买
      → 结算页（地址+优惠） → 提交订单 → 支付 → 订单生成
      → 商家发货 → 用户确认收货 → 订单完成 → 评价/售后
```

## 6.3 下单支付流程

1. 用户提交订单，系统校验库存、价格、优惠并锁定库存。
2. 系统生成订单号与订单快照，记录支付金额。
3. 用户发起支付，系统唤起第三方支付。
4. 第三方异步回调支付结果，系统验签并幂等更新订单状态。
5. 支付失败或超时则关闭订单并释放库存与优惠券。

## 6.4 商家入驻流程

1. 商家提交入驻申请（营业执照、法人、资质、类目）。
2. 平台运营对资料进行初审与复审。
3. 审核通过后创建商家账户并开通店铺；驳回则记录原因并可重新提交。
4. 商家登录商家端，完善店铺信息并发布商品。

## 6.5 售后流程

1. 用户在订单详情发起售后（退款/退货退款/换货）。
2. 商家审核申请，同意则进入退款/退货流程，拒绝则可申请平台介入。
3. 平台介入仲裁，给出处理结论。
4. 退款按实付金额原路退回，订单/库存/优惠券同步更新。

## 6.6 商品审核流程

1. 商家新增/编辑商品并提交审核。
2. 平台运营审核商品信息、价格、图片、资质。
3. 通过后商品上架；驳回则退回商家修改。

- 一个角色对应多个权限，一个账号可绑定多个角色（RBAC）。

# 8. 接口需求

## 8.1 接口设计规范

- 遵循 RESTful 风格，使用标准 HTTP 方法（GET / POST / PUT / DELETE）。
- 接口前缀统一为 `/api`，后端管理端使用 `/api/admin`，商家端 `/api/merchant`，前台 `/api/portal`。
- 返回统一结构：`{ code: 0, message: success, data: ... }`。
- 使用 OpenAPI / Swagger 自动生成接口文档。
- 认证采用 `Authorization: Bearer <token>`，敏感接口校验接口级权限。
- 参数校验使用 Bean Validation，错误码统一管理。

## 8.3 错误码规范

统一错误码规则：以业务模块划分，如 `1000` 用户域、`2000` 商品域、`3000` 订单域、`4000` 支付域、`5000` 平台域。示例：

| 错误码 | 含义 |
| --- | --- |
| 10001 | 用户不存在/被禁用 |
| 10002 | 验证码错误 |
| 20001 | 商品不存在或已下架 |
| 20002 | 库存不足 |
| 30001 | 订单状态不允许操作 |
| 40001 | 支付签名校验失败 |
| 50001 | 无操作权限 |

# 10. 验收标准

## 10.1 功能验收

- 核心交易链路（注册→浏览→下单→支付→发货→收货→评价/售后）可完整走通。
- 前台、商家端、平台端三大子系统功能符合第 4 章需求，关键功能有需求标识可追溯。
- 权限矩阵与 RBAC 生效，越权访问被拒绝。
- 订单状态流转、库存增减、优惠券使用符合业务规则。

## 10.2 性能验收

- 常规接口 P95 ≤ 500ms，核心交易接口 P95 ≤ 1000ms。
- 峰值并发下系统可用，关键页面首屏 ≤ 2s。

## 10.3 安全验收

- 密码不以明文存储，接口具备鉴权、参数校验与防注入。
- 支付回调验签有效，日志具备留痕与审计能力。
- 敏感信息脱敏展示，满足合规要求。

## 10.4 其他

- 前后端接口文档与实际一致，测试用例覆盖核心场景。
- 数据库具备备份恢复，生产配置满足运维要求。

# 11. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 库存并发超卖 | 订单/资金损失 | 使用 Redis 分布式锁 + 乐观锁，库存预占与释放 |
| 支付回调重复/丢失 | 订单状态不一致 | 回调幂等 + 对账 + 补偿任务 |
| 第三方依赖（短信/支付）故障 | 核心流程受阻 | 降级与重试，熔断与告警 |
| 数据量增长引发性能下降 | 查询变慢 | 索引优化、缓存、分库分表演进 |
| 商家/用户纠纷 | 客诉与合规风险 | 售后仲裁流程、日志留存、平台介入 |
| 权限配置不当 | 越权/数据泄露 | RBAC 最小权限，定期审计 |

# 12. 附录
